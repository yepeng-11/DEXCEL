## 三、M1：MVP——"采购登记"闭环（第 4–11 周）

目标：设计端可配置 → 发布 → 工作端在原模板内录入/粘贴/计算/关联带出/查询，数据落 MySQL 并审计。

| 编号 | 任务 | 依赖 | 验收口径 | 周次 |

| M1-A2 | 业务记录存储：biz_record + 版本链 + 审计表 | M1-A1 | 记录 CRUD + 版本回溯 + 审计查询 API 通过测试 | W5 |
| M1-A3 | 发布机制：草稿→快照→版本号，运行端只读已发布版本 | M1-A1 | 发布后模板改动不影响已发布版本；可回滚 | W6 |
| M1-A4 | 权限基座：用户/角色/登录 session + 服务端接口鉴权 | — | 未授权请求被服务端拦截（非仅前端隐藏） | W5-6 |

### M1 出口条件（Gate）——也是整个平台的闭环验收

1. 设计人员**不写代码**完成"采购登记"模板搭建并发布
2. 工作人员在**发布后的原模板内**完成：录入、50 行粘贴、公式自动计算、选供应商自动带出、保存、重新打开
3. 服务端复算覆盖前端结果；主从保存为一个事务；审计与版本可查
4. 同样的配置能力在第二个简单模板上复用成功（冒烟级即可，完整验证留给 M2）

## 六、推进节奏与并行建议

```text
周次   W1   W2   W3   W4   W5   W6   W7   W8   W9   W10  W11
S0    ▓
M0    ▓▓▓▓（工具链/表格PoC/公式PoC/存储PoC 4 人日级任务可并行）
A轨                 ▓▓▓  ▓▓▓  ▓▓▓  ▓▓▓  ▓▓▓
B轨                      ▓▓▓  ▓▓▓  ▓▓▓  ▓▓▓  ▓▓▓
C轨                           ▓▓▓  ▓▓▓  ▓▓▓  ▓▓▓  ▓▓▓
评审      Gate      Gate(M0出口)      中期检查(W8)   Gate(M1出口)
```

- **1 人推进**：严格按 A→B→C 串行，M1 预计拉长到 12–14 周；优先保 A 轨（地基），B/C 随后
- **2–3 人**：A/B/C 三轨并行，按上表依赖交接；每周一次 30 分钟对齐会同步契约变更
- **关键路径**：元数据模型（M1-A1）→ 绑定（M1-B3）→ 录入保存（M1-C2）。这条链上的任务优先级最高，其他可让路
- **契约先行**：A 轨每交付一个 API，先在 `packages/shared` 提交 TS 类型与示例 JSON，B/C 轨不等实现可先用 mock 推进

## 八、计划风险与应对

| 风险 | 触发信号 | 应对 |
|---|---|---|
| Univer 深水区（绑定/粘贴超出预期） | M0-02/03 结论为"受限" | 缩小 M1 模板复杂度（先固定单元格+重复行，交叉绑定延后） |
| 公式前后端不一致 | M0-04 不一致项多 | 收紧白名单；不一致函数在矩阵标"仅展示用，服务端不复算" |
| 元数据模型返工 | M1-B3 绑定实现与 A1 模型冲突 | W4 ER 图评审引入 B/C 轨负责人；模型变更走 ADR |
| 单人进度不足 | W6 未完成 A1-A3 | 砍 M1-C5/C6 进 M2，保"录入-保存-计算"闭环 |
| 范围蔓延 | 出现"顺手做个报表/钉钉集成" | 一律记入 M3 候选池，Gate 评审统一裁决 |
