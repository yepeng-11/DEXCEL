## 一、产品定位与边界

**定位**：面向企业业务人员的类 Excel 低代码业务平台。设计端"搭建+发布"，工作人员端"使用+办理"，MySQL 集中沉淀业务记录（含版本与审计）。

产品以现用 MyExcel 的低学习门槛为起点，参考活字格的现代应用搭建方式。它是可逐步承载采购、周报、报价等多类业务的通用平台。

**核心立场**（继承蓝图）：

- 表格是交互界面，数据库是业务事实；不把完整工作簿快照当作唯一业务事实
- **表间关联是平台核心能力，不是后期附加功能**：Excel 式界面负责"怎么填、怎么算、怎么看"，MySQL 负责集中保存，表间关联负责让供应商、物料、单据和明细通过稳定记录关系取数、查询、汇总及受控回写
- 区分三个层次：工作表公式引用（单元格位置）、业务记录关联（稳定记录 ID，本项目重点）、业务事件联动（带权限与触发条件的回写，也是本项目重点）

**明确不做**（Out of Scope，防止范围蔓延）：

- 不是完整在线 Excel，不追求 100% Excel 特性兼容
- 不是固定排产系统、采购系统或完整 ERP
- 不用跨 Sheet 单元格公式替代业务表间关系
- 不是把多个开源平台（Nop、JeecgBoot、NocoBase、Univer 等）简单堆叠
- AI、三维图识别、RAG、智能报价、完整排产、考勤报销均不进入当前主线

**两个核心使用视角**：

- 管理设计端：搭建和维护模板、数据模型、绑定、数据关系、规则、权限与流程
- 工作人员端：使用已发布应用办理业务，查询、审批和查看结果

## 二、核心概念模型

| 概念 | 说明 |
|---|---|
| 应用（Application） | 业务应用的容器，含模块、页面、工作簿与访问范围 |
| 模板（Template） | 表格应用蓝图：Sheet 结构、版式、字段绑定、公式、规则、权限、流程 |
| 应用版本（Release） | 模板发布后产生的不可变快照；工作人员端只能使用已发布版本 |
| 字段（Field） | 有业务含义的数据列，绑定数据类型与校验规则 |
| **绑定（Binding）** | 单元格/区域与数据库字段的桥梁：固定单元格、固定区域、纵向重复（明细行）、横向重复（日期周期）、二维交叉、查询显示、参数七类；需定义读写方向与保存策略 |
| 公式（Formula） | Sheet 内计算用类 Excel 公式；跨表取数用"关联引用"（按记录关系），二者不可混同 |
| 数据关系（Relation） | 表间通过稳定记录 ID 关联（如 供应商表 ←→ 采购单.供应商ID），支撑关联取数、关联查询、关联汇总、受控回写四种能力 |
| 业务记录（Record） | 用户录入产生的数据行，集中存 MySQL，带版本与审计；历史记录知道自己使用的模板版本与计算版本 |
| 流程（Flow） | 审批/流转规则，绑定到业务记录（不绑定孤立 Excel 文件），可改变节点字段状态 |

**绑定 ≠ 表间关联**：绑定解决"页面这个格子显示/保存哪个字段"；表间关联解决"当前订单如何找到供应商、明细、来源单据和汇总数据"。

## 三、总体架构

采用蓝图分层（Redis、工作流引擎等为目标态，不代表当前接入）：

```
┌─ Web 应用外壳
│   登录/导航 │ 管理设计端 │ 工作人员端 │ 查询/待办/报表
├─ 表格交互层（Univer）
│   工作簿 │ 单元格 │ 公式 │ 验证 │ 样式 │ 导入导出适配
├─ 平台应用层
│   应用定义 │ 数据模型 │ 绑定 │ 规则 │ 发布 │ 权限 │ 工作流
├─ 运行服务层
│   记录服务 │ 查询服务 │ 计算服务 │ 导入任务 │ 审计 │ 通知
├─ 扩展与集成层
│   业务函数 │ 专业计算引擎 │ API/JSON │ Excel/CSV │ 第三方系统
└─ 基础设施层
    MySQL │ Redis(后期) │ 文件/对象存储 │ 日志 │ 备份 │ 监控
```

**核心架构原则：**

1. **元数据驱动**：表格 UI、绑定、公式、权限全部由模板元数据定义，新增业务模板零代码
2. **前端即时反馈，服务端最终负责**：浏览器公式提供即时体验；金额、库存、流程条件、权限等关键计算由服务端重新验证后再持久化
3. **配置优先，代码兜底**：常见业务可视化配置；复杂扩展通过受控接口进入，不允许脚本散落单元格
4. **表格不直连数据库**：一切取数/回写统一经过业务数据服务
5. **小闭环优先**：每阶段形成可运行、可验证的纵向闭环（用户动作 → 平台行为 → 数据与权限结果 → 实际验证）

## 四、模块划分

### 4.1 设计端

1. **模板设计器**：多 Sheet、行列、合并、样式、冻结；固定单元格/重复行/重复列/交叉区域识别；XLSX 导入作为辅助起点，不承诺无损
2. **数据模型**：业务实体、字段、主从关系、字典；系统字段（创建人/时间/版本等）
3. **绑定配置**：单元格/区域 → 字段的双向绑定（七类绑定，见第二节），含读写方向、空值、类型转换、增删明细与保存策略
4. **公式与规则**：类 Excel 公式（函数白名单）、校验、默认值、自动编号、联动、事件规则、依赖图与循环引用检测
5. **数据关系配置**：关联表选择、匹配字段、取回字段、取数用途（下拉选择/自动带出/明细列表/汇总/单据入口）、触发与回写规则；无需编写 SQL
6. **权限配置**：应用 → 页面 → 数据表 → 行 → 字段/单元格 → 操作 的层级权限；角色、数据范围
7. **流程配置**：节点、条件、处理人、节点字段状态
8. **发布管理**：草稿/测试/已发布/停用/归档；发布快照、回滚、差异说明、数据结构迁移计划

### 4.2 工作人员端

1. **表格渲染与交互**：发布后的原模板版式内完成查看、录入、批量粘贴、修改（核心单据不允许"普通表单填写+保存后看表格"）
2. **数据录入**：单条录入、Excel 多行多列粘贴、导入
3. **实时计算**：前端公式即时反馈 + 服务端权威计算
4. **关联操作**：选择关联记录自动带出资料、关联查询、汇总查看
5. **查询与汇总**：记录列表、保存的查询方案、筛选排序、交叉展示
6. **审批中心**：待办、已办、审批操作、流转记录
7. **记录视图**：版本对比、修改历史、审计轨迹、回填历史记录到原模板

### 4.3 平台层

1. **元数据服务**：模板/版本的存取与校验
2. **数据服务**：记录 CRUD、关联取数（实时引用/取数快照/事件回写三种策略）、受控回写、事务与幂等
3. **公式引擎**：函数白名单解析求值，前端体验 + 后端兜底
4. **流程引擎**：第一阶段轻量状态流，接口统一，后续再评估 BPMN 引擎
5. **权限服务**：前端状态只管体验，服务端独立执行同等权限检查
6. **审计与版本**：登录、配置、发布、数据修改、流程操作全审计；记录级版本链
7. **账号与组织**：用户、角色、部门、组织范围

### 4.4 计算体系（三层，继承蓝图）

| 层 | 用途 | 典型场景 |
|---|---|---|
| 前端表格公式 | 即时反馈、临时分析 | 记录内加减乘除、IF/SUM/查找；不作为权威依据 |
| 服务端权威规则 | 保存/提交/审批时一致可审计的计算 | 金额、库存、状态、跨记录聚合、流程分支 |
| 专业计算插件（远期） | 排产、优化、大批量重算 | 通过稳定输入/输出契约接入，表格只负责配置与展示结果 |

建立**公式兼容矩阵**：每个函数记录前端/服务端支持度、导入导出行为、权威性、性能边界与测试样例；不支持的公式必须提示，不能静默算错。

### 5.2 MySQL 物理存储（关键决策点）

**元数据侧**：`tpl_application` / `tpl_template` / `tpl_release` / `tpl_sheet` / `tpl_field` / `tpl_binding` / `tpl_formula` / `tpl_relation` / `tpl_permission` / `tpl_flow`

**业务记录侧**：

- 方案 A：每模板一张物理宽表（发布时按字段 DDL 建表/加列）
- 方案 B：统一 `biz_record`（行）+ JSON 数据列
- **建议**：MVP 用 JSON 列方案（`biz_record(record_id, release_id, template_id, sheet_key, data JSON, status, version, ...)`），高频查询字段用生成列/索引；中期按模板自动生成宽表优化。M0 做对比验证。

**横向表**：`biz_record_version`、`biz_audit_log`、`flow_instance`/`flow_task`、`sys_user`/`sys_role`

**数据约定**（继承蓝图）：主从记录与关联一律用稳定 ID，不用行号/名称/格子位置充当业务主键；定点金额用十进制文本传输保存，不用浮点；日期沿用 `YYYY-MM-DD`。

## 六、技术选型与关键决策点

### 6.1 技术选型（已定案 2026-09-09）

| 层面 | 选型 | 说明 |
|---|---|---|
| 前端框架 | Vue 3 + Vite + **TypeScript** | SFC、Composition API；引入 UI 组件库（Element Plus 或 Arco Design，M0 定其一）加速设计端配置界面开发 |
| 状态与路由 | Pinia + Vue Router | 常规配套 |
| 表格内核 | Univer（@univerjs/presets） | 只作表格交互底座，不当完整业务平台；Univer 内部基于 React 渲染，通过挂载实例方式嵌入 Vue 应用（官方支持），两者互不干扰 |
| 前端请求 | 浏览器 fetch，统一 api 封装 | 同源 `/api` |
| **后端** | **Node.js + NestJS（TypeScript）单体** | 已定案（否决全 Java / Java+Node 混合路线，理由见 6.3）。按"数据服务 / 计算服务"边界组织模块，为将来拆分专业计算服务留接口 |
| 公式引擎 | 复用 Univer 公式引擎于 Node 端复算 | **前后端引擎同构**：一套函数白名单、一份兼容矩阵、一套测试用例，保证前后端计算结果一致 |
| ORM/DB 访问 | mysql2 连接池 + 轻量查询层 | 不引重型 ORM；元数据与业务记录同库 |
| 业务数据库 | MySQL 8.4 单库（InnoDB） | 平台元数据 + 业务数据 + 审计；**放弃蓝图中的 SQLite/双库过渡** |
| 缓存/会话 | 服务端内存 session 起步 | 不引入 Redis；架构留接口，用户量上来再加 |
| 文件存储 | 本地磁盘起步，接口抽象 | 附件/导入导出/备份，后期可换 MinIO |
| Excel 转换 | SheetJS（固定版本来源） | 导入导出适配 |
| 工作流 | 自研轻量状态机 | 第一阶段不接 Flowable/BPMN，接口统一 |
| 测试 | Vitest（或 Jest） | API、存储、契约、公式兼容矩阵用例 |
| 部署 | Windows 本地起步，配置可迁移 | 无 Docker 前置要求；后续可容器化 |

### 6.2 关键决策点

| # | 决策点 | 结论/建议 |
|---|---|---|
| 1 | 表格内核 | 已定 Univer；M0 重点验证 200 列级宽表渲染、冻结、粘贴、公式体验（参考 `自动排产.xls` 样本：67 行 × 197 列、1168 个公式单元格） |
| 2 | 公式范围 | 首批白名单以真实样本实际用到的函数为准（IF、VLOOKUP、SUMIF/SUMIFS、SUM、IFERROR、MIN、INDEX、MATCH 等），不盲目追求数量；不做跨 Sheet 单元格坐标引用做业务关联 |
| 3 | 关联取数执行 | 关联引用设计端显式配置，运行期由数据服务解析为 SQL/查询；每条取数规则须选择策略：实时引用 / 取数快照 / 事件回写。物料改价不得自动重写已批准订单的成交单价 |
| 4 | 关联异常处理 | 多匹配阻止或要求明确选择；区分"无记录/为零/无权限/取数失败"；被引用记录默认限制删除；回写需独立授权+审计；防循环触发 |
| 5 | 发布版本与存量数据 | 发布即不可变快照；历史记录关联创建时版本；升级迁移用显式脚本，M1 就立规矩 |
| 6 | 粘贴体验 | Excel 多行多列粘贴解析、类型匹配与错误提示是核心体验点，MVP 必须做好 |
| 7 | 性能 | 大表分页/虚拟滚动/可视区域渲染；汇总走服务端聚合；查询有界分页，避免逐单元格请求数据库 |
| 8 | 业务记录存储 | JSON 列 vs 宽表，见 5.2，M0 对比验证 |

### 6.3 后端路线决策记录（2026-09-09 定案）

**结论：全 Node.js + NestJS 单体（TypeScript）。** 否决了另外两条路线：

| 路线 | 否决/保留原因 |
|---|---|
| 全 Java Spring Boot | 公式引擎无现成同款：POI 求值器函数覆盖与语义不足，自研引擎长期维护税重，GraalVM 内嵌 JS 引擎引入 polyglot 复杂度。且失去前后端共享 TS 契约优势。保留远期可能：若未来上专业排产计算（OptaPlanner/Timefold），按计算服务接口外挂 |
| Java 主服务 + Node 计算服务 | 可行但双服务部署/运维/契约成本起步即付，M1 无必要 |

**定案理由**：

1. **公式引擎前后端同构**是本项目核心机制（前端即时计算 + 服务端权威复算），Univer 引擎可直接在 Node 端复用，结果天然一致
2. 元数据 DSL、绑定校验、契约前后端共享一份 TS 代码
3. 单体单部署，事务、权限、审计在同一服务内闭环，无 RPC/分布式事务问题

**架构护栏（无论将来是否拆分，都按此边界组织代码）**：

- 后端模块按"**数据服务**（元数据/记录/权限/流程/审计）"与"**计算服务**（公式求值/依赖图，无副作用、不连库）"两个边界划分；M1 在同一进程内实现，将来可原样拆出独立服务或外挂 Java 专业计算，接口不变
- 计算服务输入为"记录上下文 + 关联数据快照 + 公式定义"，输出为计算结果与错误清单，不写库
- 契约从前端到后端共享 `shared/` 目录 TS 类型；对外 API 以 OpenAPI 描述

## 七、里程碑建议

| 阶段 | 目标 | 主要产出 |
|---|---|---|
| **M0 调研与 PoC**（2-3 周） | 验证最大技术风险 | ① Univer PoC：宽表渲染/粘贴/公式/绑定可行性；② 存储方案 PoC：JSON vs 宽表对比表；③ 技术决策记录（含公式兼容矩阵初版） |
| **M1 MVP**（6-8 周） | 一个真实业务跑通（建议"采购登记"标杆） | 设计端：数据模型+绑定+公式+简单权限+发布；工作端：原模板内录入/粘贴/计算/关联带出/查询；MySQL 记录+审计。验收：设计配置驱动、能在另一模板复用，不是为一张单写死代码 |
| **M2 平台化**（4-6 周） | 通用性验证 | 跨表关联汇总、受控回写（审批触发）、流程审批、第二个业务模板（如周报）零代码搭建成功 |
| **M3 完善与推广**（持续） | 多业务承载 | 版本升级与数据迁移工具、行级权限、导入导出增强、性能优化、报表导出（复杂中国式报表届时单独评估报表引擎） |

### M0 PoC 验收标准

1. **Univer 验证表**：200 列横向滚动与冻结、Excel→系统粘贴、白名单公式求值、绑定驱动数据读写，四项各给出可行/受限/不可行结论
2. **存储对比表**：JSON 方案 vs 宽表方案在写入、查询、模板变更成本、审计实现难度四个维度打分，形成结论

## 八、主要风险

1. **范围蔓延**：被要求做"完整 Excel"或"完整 ERP" → 用第一节边界清单对齐干系人
2. **公式引擎复杂度失控** → 严守白名单 + 兼容矩阵，业务关联一律走关系配置
3. **模板升级与存量数据兼容** → 发布即快照 + 迁移脚本机制在 M1 立规矩
4. **Univer 能力边界**（超宽表性能、粘贴、复杂公式语义） → M0 验证后锁定，预留适配层隔离依赖
5. **性能**：大模板提前设计分页、可视区域渲染与服务端聚合
6. **文档与实际脱节**：蓝图引用的原型代码不在本仓库 → 以本文件为当前规划基线，差异见第九节
